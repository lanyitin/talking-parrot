# ADR-0001: 跨平台轉錄後端選擇策略

## Status

Accepted

## Context

本系統需要在三種作業系統上執行 Whisper 轉錄：

- **macOS**（Apple Silicon）：`faster-whisper` 不支援 Metal GPU 加速，但 `mlx-whisper` 針對 Apple Silicon 的 MLX 框架最佳化，效能顯著較佳。
- **Windows / Linux**（x86-64 + NVIDIA GPU）：`faster-whisper` 以 CTranslate2 後端執行，CUDA 加速成熟且穩定。

兩個套件的 Python API 不相容，若在 `TranscriptionStage` 內直接以 `if sys.platform == "darwin"` 區分，會同時違反：
- **OCP**：每次新增平台都需修改 Stage 程式碼
- **DIP**：高層 Stage 直接依賴具體的平台套件
- **SRP**：Stage 同時承擔「平台偵測」與「轉錄邏輯」兩個職責

## Decision

採用**介面 + 工廠**模式：

1. 定義 `TranscriptionBackend` 抽象介面，只暴露 `transcribe()` 方法（見 [[pipeline-module-interfaces]]）。
2. `FasterWhisperBackend` 與 `MLXWhisperBackend` 各自實作此介面，封裝平台特定的初始化與呼叫細節。
3. `TranscriptionBackendFactory` 在應用程式入口點（`cli.py`）被呼叫，根據以下優先序決定使用哪個後端：
   1. 環境變數 `TRANSCRIPTION_BACKEND`（允許強制覆蓋，用於測試或特殊需求）
   2. `sys.platform` 自動偵測
4. 建立好的 `TranscriptionBackend` 實例透過建構子注入到 `TranscriptionStage`，Stage 完全不知道具體後端。

## Rationale

**為何不用 `try/import` 動態偵測？**
動態 import 會讓依賴關係隱藏在執行期，無法在安裝時期透過 `pyproject.toml` optional dependencies 明確聲明，違反 Factor II（明確宣告依賴）。

**為何不用 plugin/entry_point 機制？**
目前只有兩個已知的後端實作，plugin 機制的複雜度超過需求。若未來出現第三個後端（例如 `whisper.cpp` binding），只需新增一個實作類別與工廠判斷規則，不需要修改現有程式碼（OCP）。

**為何用環境變數覆蓋而非設定檔？**
後端選擇屬於**部署環境**的差異，不是使用者的轉錄設定，因此放在環境變數而非 YAML，符合 Factor III。

## Consequences

**正面**
- `TranscriptionStage` 完全與平台解耦，可以獨立單元測試（注入 mock backend）
- 新增後端不修改任何現有程式碼
- 平台差異集中在一個地方（`factory.py`），易於維護

**需注意的取捨**
- 安裝時需手動選擇正確的 optional dependency 群組；若用錯套件，`TranscriptionBackendFactory` 應在建立時立即拋出明確的錯誤訊息，而非在轉錄時才失敗
- `mlx-whisper` 與 `faster-whisper` 的模型名稱對應可能有差異，須在各自的 Backend 實作內處理映射，不洩漏至介面層

## SOLID / 12-Factor Alignment

| 原則 | 如何滿足 |
|------|---------|
| OCP | 新增後端只需新增實作類別，不修改 Stage |
| DIP | `TranscriptionStage` 依賴 `TranscriptionBackend` 介面，不依賴具體實作 |
| LSP | `FasterWhisperBackend` 與 `MLXWhisperBackend` 可被透明替換 |
| SRP | 平台偵測邏輯集中在 `TranscriptionBackendFactory` |
| Factor II | 各平台的套件依賴明確宣告在 optional dependency 群組 |
| Factor III | 後端選擇可透過 `TRANSCRIPTION_BACKEND` 環境變數覆蓋 |
