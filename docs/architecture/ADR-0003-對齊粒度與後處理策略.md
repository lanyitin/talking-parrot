# ADR-0003: 對齊粒度與後處理策略設計

## Status

Accepted

## Context

Force Alignment 使用 wav2vec2 模型，不同語言的模型輸出粒度不同：

- **英文（en）**：wav2vec2 輸出以詞（word）為單位的時間戳記（word-level alignment）
- **日文（ja）**：日文無詞間空格，wav2vec2 輸出以字元（character）為單位（character-level alignment）
- **未來語言**：可能出現音節級（syllable-level）或其他粒度

後處理（Post-Processing）的核心工作是合併過短字幕與切分過長字幕。這項工作必須在「語意邊界」處切割，才能避免在詞中間斷句。問題在於：

1. word-level 對齊時，切割點應落在詞邊界（兩個 word token 之間）。
2. character-level 對齊時，切割點應落在字元邊界，需要依照語言特性（例如日文標點符號、句型節奏）判斷。
3. alignment **未啟用**時，系統完全沒有邊界資訊，只能依據時間長度與靜音間隔做近似切割。

若在 `PostProcessingStage` 內以 `if/elif` 直接判斷語言或粒度，會導致：

- **OCP 違反**：新增語言或粒度需修改 Stage 程式碼
- **SRP 違反**：Stage 同時承擔「粒度偵測」與「後處理執行」兩個職責
- **DIP 違反**：高層 Stage 直接依賴具體語言邏輯

## Decision

採用 **`AlignmentGranularity` enum 作為策略選擇鍵**，搭配工廠模式：

1. 定義 `AlignmentGranularity` enum（`WORD`、`CHARACTER`），由 `AlignmentBackend` 介面的 `granularity` 屬性對外暴露。

2. `AlignmentStage` 執行對齊後，將 `granularity` 寫入 `PipelineContext`。若 alignment 未啟用，`ctx.alignment_granularity` 為 `None`。

3. 定義 `GranularityAwareProcessorFactory` 介面，`create(granularity)` 依粒度值回傳對應的 `SubtitleProcessor` 清單：
   - `WORD` → `[WordBoundaryMergeProcessor, WordBoundarySplitProcessor]`
   - `CHARACTER` → `[CharacterBoundaryMergeProcessor, CharacterBoundarySplitProcessor]`
   - `None` → `[TimeBasedMergeProcessor, TimeBasedSplitProcessor]`（fallback）

4. `PostProcessingStage` 只依賴 `GranularityAwareProcessorFactory` 介面，不知道任何語言或粒度的具體判斷邏輯。

5. 各 `AlignmentBackend` 實作負責宣告自己的 `granularity`（而非由外部配置指定），確保粒度與模型實作緊密綁定，避免設定錯誤。

6. `AlignmentBackendFactory` 維護 `(language, granularity) -> backend_class` 的二維註冊表，並接受 `(language, granularity_pref)` 參數：
   - `granularity_pref == AUTO`：使用該語言的預設 backend（例：英文 → WORD、日文 → CHARACTER）
   - `granularity_pref == WORD / CHARACTER`：強制選用對應粒度的 backend，無對應實作時拋出 `UnsupportedAlignmentBackendError`

   此設計同時支援「同語言多粒度 backend」的未來擴充：例如若日後新增 `JapaneseWordAlignmentBackend`（MeCab 斷詞 + word-level wav2vec2），只需在註冊表新增 `(ja, WORD)` 條目，使用者於 YAML 設定 `align.granularity: word` 即可切換，不修改 Factory 路由邏輯（OCP）。

## Rationale

**為何以 enum 而非字串或語言代碼作為策略鍵？**

若以語言代碼（`"en"`、`"ja"`）作為策略選擇鍵，工廠需要知道每個語言對應哪種粒度，實際上是把「語言→粒度」的映射重複了一遍。`AlignmentGranularity` enum 是已知粒度的封閉集合，工廠只需對應有限的幾個值，不需要知道語言細節。當新語言使用已知粒度時，只需新增 `AlignmentBackend` 實作，工廠完全不需要變動。

**為何 `granularity` 由 `AlignmentBackend` 自己宣告，而非由設定檔指定？**

粒度是模型特性，不是使用者設定。若允許使用者在 YAML 中指定粒度，可能出現「模型輸出 character-level 但設定宣稱 word-level」的不一致，導致後處理邏輯錯誤。由實作類別宣告可確保粒度資訊的來源唯一（Single Source of Truth）。

**為何 fallback 不是「停用後處理」而是「切換到 TimeBasedProcessor」？**

即使沒有對齊資訊，字幕仍然需要基本的切割與合併處理（例如單句超過 6 秒必須切分）。完全跳過後處理會使輸出字幕品質不可接受。`TimeBasedProcessor` 是退而求其次的近似解，不依賴對齊資訊，可在 alignment 未啟用的情境下安全運作。

**為何不使用 duck-typing 直接讓 processor 自行偵測輸入？**

若每個 Processor 自行判斷輸入是否含有對齊資訊，會產生分散的條件邏輯，且各 Processor 需要承擔「輸入驗證」職責，違反 SRP。集中在工廠選擇策略，讓 Processor 只專注於自己的切割/合併邏輯。

## Consequences

**正面**

- `PostProcessingStage` 完全與語言和粒度解耦，可獨立單元測試（注入 mock factory）
- 新增語言（例如韓文，若粒度為 `WORD`）只需新增 `AlignmentBackend` 實作，工廠和 Stage 完全不需修改
- 新增粒度類型只需在 enum 新增值、工廠新增分支、實作對應 Processor，不修改現有程式碼（OCP）
- `TimeBasedProcessor` fallback 確保 alignment 關閉時系統仍可正常輸出合理字幕
- `granularity` 由 `AlignmentBackend` 宣告，消除設定不一致的風險

**需注意的取捨**

- `AlignmentGranularity` enum 是封閉集合，若未來出現完全新型粒度（例如音節級），需更新 enum 與工廠，但這是有意識的「封閉點」，變更範圍可控
- 三態狀態以 `AlignmentStatus` enum（`DISABLED / SUCCESS / FAILED`）明確記錄，避免 `None` 同時代表「未啟用」與「失敗」；`PostProcessingStage` 在 `FAILED` 時除了 fallback 還必須寫 WARNING log，提示使用者調查 alignment 失敗原因
- `TimeBasedProcessor` 的切割品質低於對齊版本，應在系統日誌中明確記錄「使用 fallback 後處理」，方便使用者評估是否啟用 alignment

## SOLID / 12-Factor Alignment

| 原則 | 如何滿足 |
|------|---------|
| SRP | `AlignmentBackend` 只負責對齊；`GranularityAwareProcessorFactory` 只負責策略選擇；`SubtitleProcessor` 只負責執行單一後處理步驟 |
| OCP | 新增語言後端或新增粒度類型時，不修改 Stage 或現有 Processor |
| LSP | 所有 `AlignmentBackend` 實作（English / Japanese）可被透明替換；所有 `SubtitleProcessor` 實作可被透明替換 |
| ISP | `AlignmentBackend` 只暴露 `align()` 與 `granularity`；`SubtitleProcessor` 只暴露 `process()` |
| DIP | `AlignmentStage` 依賴 `AlignmentBackend` 介面；`PostProcessingStage` 依賴 `GranularityAwareProcessorFactory` 介面，兩者皆由入口點注入 |
| Factor III (Config) | 語言設定由外部 YAML 傳入，`AlignmentBackendFactory` 依此路由；alignment 啟用/停用亦由 YAML 控制，不硬編碼 |
| Factor IV (Backing services) | wav2vec2 模型視為可替換的附加資源，透過 `AlignmentBackend` 介面解耦 |
| Factor VI (Stateless) | `granularity` 存於 `PipelineContext`，Stage 無狀態 |
| Factor XI (Logs) | fallback 觸發事件寫入 stdout 日誌，由上層基礎設施管理 |

## Future Work

- **同語言多粒度 backend**：目前每種語言只有一個 backend 實作（英文 word-level、日文 character-level）。未來若日文需要 word-level 對齊（例如配合 MeCab 斷詞 + word-level wav2vec2 模型），只需新增 `JapaneseWordAlignmentBackend` 並註冊 `(ja, WORD)` 條目，使用者透過 `align.granularity: word` 即可切換。
- **更細粒度（例如音節）**：`AlignmentGranularity` enum 是封閉集合，新增粒度值需同步更新此 enum、`GranularityAwareProcessorFactory` 與對應 Processor 群組。屬於有意識的封閉點，變更範圍可控。
